# MapVibes — Functional Specification

Status: v1.4.0 — annotation labels on the map and the phone viewer delivered (labels printed relative to the sheet and scaling with the map, and the narrow layout of the exported viewer, with the desktop proven unchanged). See the changelog below.

MapVibes is a static, client-side web application: a spreadsheet-to-map visualisation tool. It has no backend, no database, and no server-side processing. Everything runs locally in the browser.

## Hard constraints

1. Fully client-side static web application (HTML, CSS, JavaScript).
2. No network calls at runtime: no uploads, no analytics, no telemetry, no CDN fetches during use. All fonts, styles, and scripts are bundled locally. The single exception is the explicit, user-initiated, clearly labelled fetch of open map data (FR-31): it is the application's only network operation; it is never made automatically; no user data is ever included in its requests; its result is embedded into the work state like any other background. All other operations, including the exported presentation file, remain fully offline.
3. The application must function fully with no internet connection (airplane-mode test applies to every delivery). The guarantee holds at all times except during the labelled open-map fetch (FR-31); with no connection, that control is disabled with a clear message and every other function works.
4. All state remains on the user's device: files are read in the browser and written only on explicit export or save.
5. No hardcoded column names, headers, or business terminology: the application must work with arbitrary header names in any language. (Note for FR-41: the bundled demo is example data, a generic and fictional fixture from example-data loaded through the normal import path; its neutral headers and invented names are data, never used by the application's logic. Amended in v1.3.1: the fixture is carried in example-data in both interface languages, and the demo loads in the interface language; the translations are data of the fixture, not application text, and no logic reads them.) (Note for FR-30, amended in v1.3.0 on the owner's decision: the starter columns of an empty list are interface text in the current language with neutral words (Name, Start year, End year, Note; Namn, Startår, Slutår, Anteckning), created as ordinary, editable manual columns; their roles are assigned by column key, never by name, and no logic reads their labels.)
6. No automatic selection or filtering logic deciding which rows "fit": data cleaning is deliberately a manual process performed by the user. The application provides generic list conveniences only.

## Functional requirements

- FR-1: Ingest a spreadsheet (xlsx) by file drop or file picker; parse all columns; surface parsing errors clearly. Ingestion is direct: importing a spreadsheet populates the list immediately with all of the file's columns, named by the file's own headers, shown as-is; no configuration dialog interrupts the import, and no header names are hardcoded. Columns are shown and hidden in the list itself. Role assignment also takes place in the list: a per-column control in the list header assigns the optional roles identifier, name/title, start date, end date, area/grouping, and status (each role to at most one column). All column data is treated as generic text. The name/title is the display name of an item, used by the list, the marker labels, and the at-a-glance panel; where it is unassigned or empty, the display name falls back to the identifier value, and otherwise to the item's number. (Amended for FR-43 and FR-35: the roles include program and note.)
- FR-2: Support the user's manual cleaning process: present all ingested rows in the list; the user removes rows by hand. The list shall support: sorting by column; setting the marker colour per row; showing and hiding columns; filtering on column values, including empty and non-empty cells in a chosen column; and selecting multiple or all rows for bulk deletion. Show running counts of retained and removed rows.
- FR-3: Assign sequential presentation numbers, starting at 1, globally across all items. When rows are removed or added after numbering, numbers regenerate so the sequence remains continuous. (Amended for FR-17: the global numbering is the default; a grouped numbering by area can be chosen explicitly instead, and switching back restores the global numbering.)
- FR-4: Display a zoomable, pannable background map image supplied by the user.
- FR-5: Allow the user to place, move, and remove numbered markers, with the colours green (default), blue, yellow, and red. (Amended for FR-45, on the owner's decision: green stays the initial colour of a new row; the application never colours items from their data and gives the colours no meanings; the user names them.)
- FR-6: Display a legend at the bottom of the map view.
- FR-7: Display a details panel for a selected item. Selecting an item (a line in the list, its marker in the Map segment, or its entry in the at-a-glance panel) opens a details panel showing all of the item's data: number, name/title, colour, symbol, every column with its value, and its comments. The panel follows the selection and closes cleanly.
- FR-8: The main view shows all areas; the user may zoom in or select a box/region of interest to focus on one area.
- FR-9: Allow the user to add items manually (not originating from the spreadsheet), with the same fields, colour coding, sequential numbering, and marker placement as imported items.
- FR-10: Allow the user to edit any item's values, including values that came from an import, in the list and in the details panel; edits count as unsaved changes and are stored in the work state.
- FR-11: Export a single self-contained interactive HTML file (all data, map image, and application logic embedded in one file) that opens locally in any browser with zoom, legend, and per-marker details, requiring no server and no internet connection. This is the primary presentation format. An explicit export action produces one standalone HTML file, the viewer and the work state to be shared embedded in it, that opens by double-click on any machine, fully offline, with no network calls and no dependencies. (Amended in v1.3.0: the interactive export is the primary and most prominent sharing action in the Presentation segment; the PDF and PowerPoint actions sit beside it as secondary actions.)
- FR-12: PDF and PowerPoint export is a secondary, optional feature. If implemented: the map with legend, followed by the relevant rows as a well-formatted table, with pagination or equivalent handling for large numbers of rows. (Amended in v1.2.0, with FR-50 to FR-52, as follows. The PDF document's first page is the visible presentation stage: the map with its background, the markers with their numbers, the annotations, and the legend, faithful to what is shown; the following pages hold the shown items as a table of the shown columns in the list's column order, led by the number, paginated, with the column headings repeated on every page. The PowerPoint document's first slide carries the rendered presentation stage as an image; the following slides hold the same table, paginated, as native table slides. Both documents are written entirely in the browser, with no libraries and no network.)
- FR-13: Support saving and reloading work state locally (an overlay/state file): marker positions, manually added items, field edits, comments, and the column mapping, so no work is lost between sessions. (Amended in v1.1.0: work-state schema version 6 adds the program vocabulary, the colour labels, the at-a-glance columns, the annotations, and the scale of backgrounds rendered from OpenStreetMap data; versions 1 to 5 still open.) (Amended in v1.3.0: work-state schema version 7 adds the numbering mode and the list view (FR-17), the symbol labels (FR-54), and the comments' edit dates (FR-15); versions 1 to 6 still open.)
- FR-14: Support importing a previously exported interactive map file so existing markers can be compared with a newly imported spreadsheet; reconciliation is performed by the user, not automatically. An exported file can be opened back into the application, which shows a comparison of its items with the current work, matched by the identifier column: matched items with markers, matched items without markers, items present only in the file, and items present only in the current work. Marker positions from the file are adopted for matched items only through an explicit user action, as an unsaved change. (Amended in v1.3.0: the comparison shows the numbers consistently with the chosen numbering mode, for the exported items and the current items alike.)
- FR-15: Comments. Each item carries comments: entries of plain text with a date, appended in the details panel; entries can be removed; comments show in the details panel and in the presentation data card (FR-35). (Amended in v1.3.0, on the owner's decision: comments are editable where they are created, in the details panel of the Information and Map segments; an edited comment keeps its creation date and records its edit date, and both are shown. The Presentation segment and the exported viewer stay view-only, FR-35.)
- FR-16: Present the item list alongside the map; selecting a line displays all details and comments for that item in the details panel (FR-7). (Amended in v1.3.0: opening or closing the details panel, which narrows or widens the Map stage, refits the map view so that the map stays in view: a fitted view becomes the fitted view of the new stage size; a zoomed view keeps its centre and shrinks with a narrowing stage, so that it keeps showing what it showed.)
- FR-17: Generate sequential presentation numbers in the list per FR-3, with the list grouped or groupable by area for readability. Grouped numbering (amended in v1.1.0: its axis is the program, FR-43): an explicit numbering mode numbers the items sequentially within each program, shown as the program's position and the number within it (for example 2.3); the programs follow the order of the program list, then program values not in the list in order of first appearance; items without a program are numbered 1, 2, 3 and onward among themselves (on the owner's decision), so that every number is unique; the numbers are the same in the list, on the markers, in every panel and card, in exported files, and in the comparison, and regenerate on every change as the global numbers do. The mode requires the program role and says so clearly when it is not assigned. Group-by-area view: the list can be shown grouped by area value, in collapsible sections, with sorting and filtering working within the sections; the flat list remains. (Amended in v1.3.0: the numbering mode and the list view are saved in the work-state file, FR-13.)
- FR-18: Support drag-and-drop of an item from the list onto the map to create its numbered, colour-coded marker at the drop position.
- FR-19: Provide a UI language toggle between Swedish and English, with all interface strings externalised in translation files; the choice is remembered. On first run (no remembered choice), the interface is in Swedish. (Amended in v1.3.0: translation parity. Every user-visible string exists in both languages, including the symbol names and every surface added since; a test over the string tables fails on any missing or untranslated entry.)
- FR-20: Provide dark, light, and follow-system theme options, defaulting to follow-system; the choice is remembered. The exported interactive map file shall respect the same theming options: the exported viewer opens in the language and theme of the exported work (follow-system following the viewing machine) and offers the same language and theme controls; choices made in the viewer are not remembered, so that viewing an export never changes the application's stored preferences.
- FR-21: All user preferences (language, theme, column mapping, view state) are stored locally on the device only (browser local storage or the state file), never transmitted.
- FR-22: Segment structure. The application is organised into three segments with a clear flow: Information (list, cleaning, numbering), Map (background, markers, placement), and Presentation (final view and export). Work performed in one segment is never lost by moving to another segment.
- FR-23: Saved column presets. The current column configuration (shown and hidden columns, and role assignments) can be saved under a name. When a later import has the same headers, the matching preset applies automatically; presets can also be applied, switched, and removed by the user. Presets persist in the work-state file and in local storage where available (FR-21).
- FR-24: Manually added columns. The user can add columns by hand; such columns participate in sorting, filtering, and grouping exactly like imported columns.
- FR-25: Map background import from PDF documents. In addition to image files (FR-4), the background can be loaded from a PDF document: the user selects the page, and the rendered page becomes the background image on the same viewport. PDF rendering uses a fully bundled library; no CDN or network access is involved.
- FR-26: Marker symbol library. Beyond the four colours (FR-5), a library of marker symbols is available, and the symbol is changeable per marker. The library holds geometric shapes and eight icons: light bulb, magnifying glass, gear, pause bars, cross, checkmark, crossed hammer and shovel, and lightning bolt, rendered as vector icons with at least 4.5:1 contrast against the marker fill in both themes. (Amended in v1.1.0 to add the lightning bolt, drawn in the same stroked family as the crossed hammer and shovel, selectable per marker, assignable per status, and shown in the legend; implemented in v1.2.0.)
- FR-27: Presentation mode with per-item and per-layer visibility toggles. Items and layers excluded by the user are absent from the exported presentation.
- FR-28: At-a-glance panel. A panel beside the map shows only the items currently visible in the viewport, updating live as the viewport changes, with cross-highlighting between list entries and markers.
- FR-29: Design quality bar. The interface maintains a consistent visual language, spacing, and theming across the light and dark modes; where practical, this is pinned by automated DOM and CSS assertions.
- FR-30: Manual population of the entire list. An empty list can be started with no import at all, so that the application is fully usable where no files can be opened; rows and columns are then added and edited by hand. (Amended in v1.3.0, on the owner's decision: "Start an empty list" opens with four starter columns, Name, Start year, End year, and Note in the current language, with the name, start, end, and note roles already assigned; they are ordinary manual columns, freely renamed, given other roles, or hidden. See hard constraint 5.)
- FR-31: Open-map backgrounds. OpenStreetMap XML (.osm) files can be loaded locally and rendered as map backgrounds. In addition, an explicit, clearly labelled, user-initiated action fetches open map data by place name or bounding box from open services and renders it the same way (see hard constraints 2 and 3).
- FR-32: Area vocabulary. The area/grouping role is choose-from: each cell of the area column offers a combobox in which an existing value is picked or a new value is typed. The list of values is managed by the user in a panel (add, rename, remove), with an action that collects all values currently present in the column. The list is empty by default and persists in the work state and in presets.
- FR-33: Status role and vocabulary. A column can be assigned the status role; its values are chosen, through a combobox in each cell, from a status list managed by the user in a panel (add, rename, remove, reorder, and assign a symbol from the symbol library to each status). The list is empty by default and persists in the work state and in presets. No status words are predefined.
- FR-34: Status-to-symbol assignment. An explicit toggle "assign marker symbols from status", off by default. While it is off, choosing a status never changes any marker's symbol; symbols change only per marker in the Map segment. While it is on, each item whose marker has no manually chosen symbol shows the symbol of its status; a manually chosen symbol is never overridden.
- FR-35: Presentation interactivity. In the Presentation segment, markers are clickable: clicking a marker opens a view-only floating data card with the same details as the details panel (FR-7), closable without side effects. Nothing can be edited in the Presentation segment. (Amended for FR-37 in v1.1.0: the card is content-first and repeats nothing the marker or its header already shows.)
- FR-36: Zoom and pan parity. The Presentation segment's viewport matches the Map segment's exactly: wheel zoom at the cursor, control zoom, drag pan, fit view, and touch pinch; viewport motion is smooth.
- FR-37: Presentation design bar. The Presentation segment holds up when projected: typography sized for distance, at least 4.5:1 text contrast over any background, smooth viewport motion, and a subtle entrance and exit for the data card; pinned by DOM and CSS assertions where practicable. (Amended in v1.1.0: the card is redesigned content-first. It shows no number, colour, or symbol lines (the marker shows them) and no name line repeating its header. The note (the column with the note role, FR-1) and the comments come first, as the headliners; the structured fields (identifier, area, status, program, start and end) follow in a compact aligned grid; the linked annotations are named (FR-48). The type scale is compact with a 16 pixel floor, replacing the projection sizes; contrast stays at 4.5:1 or better over any background. Pinned by DOM and CSS assertions.)
- Scope note to FR-32 and FR-33: the comboboxes apply to every row, imported rows included. (Since v0.8.0, FR-10 makes every value editable; the area and status columns keep their combobox cells.)
- Scope note to FR-35: "nothing can be edited" applies to the item data (values, comments, colours, symbols, and marker positions). The per-item visibility toggles of FR-27 configure the presentation itself and remain in the Presentation segment's visibility list; the marker visibility control that clicking a presentation marker opened up to v0.7.0 is replaced by the data card.
- FR-38: Exported viewer. The exported file is view-only: it reproduces the presentation with the map stage, background, and markers, the legend, the at-a-glance panel, the item list, and the clickable data cards with comments. Zoom, pan, and card selection work; nothing can be edited, moved, or saved there. The viewer is the application's own presentation, list, at-a-glance, and card implementation running in a view-only mode, so that the export cannot drift from the application. Items keep the numbers they have in the Presentation segment. (Amended in v1.3.0: the exported viewer opens at the view the file carries, its position and zoom, rather than fitting the view.) (Amended in v1.3.1 by the owner's directive: the viewer renders no item list. The recipient gets the stage, the at-a-glance panel, the legend, and the cards; the embedded data stays in the file in readable form exactly as the export dialog discloses, and the dialog says that the data is in the file's source, including what the presentation does not show.)
- FR-39: Honest export. Items switched off for the presentation (FR-27) and rows removed from the list are absent from the exported file, not hidden in it. The exported file holds its data in readable form, and the export dialog states plainly, before the file is produced, what the file will contain, so that the user knows exactly what is being shared. (Amended in v1.3.0 by FR-53: the export dialog also selects what to share.)
- FR-40: Export format versioning. The data embedded in an exported file carries its own format name and version, with the same discipline as the work-state file: the current version is written; older versions are read and migrated; any other version is rejected with a clear message. (Amended in v1.1.0: export format version 2 adds the annotations, the colour labels, the program groups, and the at-a-glance columns; version 1 is still read.)
- FR-41: Full-test demo. A "Load demo" action loads a complete, ready-to-operate fictional scenario, labelled as example data and guarded by the unsaved-changes confirmation, fully offline: the synthetic town map fixture as background; a list of about a dozen invented items with all roles assigned; a saved column preset matching the demo's headers; an invented area vocabulary; an invented status vocabulary with symbols assigned; start and end years; comments on several items; markers placed in a deliberately varied arrangement (colours and symbols varied, some clustered, some near the edges); and the presentation ready to open. All demo data is generic and fictional; it gives every control something to act on. (Amended in v1.1.0: the demo also has an invented program vocabulary with programs spanning areas, user-named colour labels, a note column, painted footprints (a polygon linked to one item, a free annotation elsewhere, one dashed line), and configured at-a-glance columns.) (Amended in v1.3.1, interface-language coherence: everything the application provides follows the interface language, the demo's data-carried labels included, and everything the user types stays the user's own words. The demo loads in the interface language: its headers, texts, comments, vocabularies (areas, programs, and statuses, with the values that carry them), colour labels, annotation labels, and preset name. When the language is switched while the demo is loaded, each provided label the user has not renamed (the colour labels, the vocabulary values with the cells that hold them, and the annotation labels) takes its counterpart in the new language; a label the user typed is kept as typed; the list's own headers and texts stay as loaded, since they are the work's columns and values, and so does the demo's preset, which matches those headers. Loading the demo in one language replaces the other language's demo preset if it is unchanged. Replacing the demo with other work (an import or an empty list) discards the demo's provided colour labels and at-a-glance choice with it.)
- FR-42: Information density. The operator's surfaces (the details panel, the data surfaces of the Map segment, the at-a-glance entries, and the dialogs) are dense: tighter spacing, aligned field grids (two columns where the width allows), and more information per screen without loss of legibility, with no oversized gaps or padding around the information itself. The presentation data card (FR-35, FR-37) keeps its projection sizes. The density is pinned by DOM and CSS assertions. (Amended in v1.1.0: the new panels (program, colour labels, at-a-glance columns, annotation tools) are operator surfaces under this rule; the presentation card keeps its own compact scale, FR-37.)
- FR-43: Program role and vocabulary. A column can be assigned the program role; its values are chosen from a user-managed program vocabulary (combobox cells: pick an existing value or type a new one; a management panel; persistence in the work state and presets), the same pattern as areas (FR-32) and statuses (FR-33). A program consists of several items that can be separate in time and space; most items belong to no program, and an empty value is normal. The English interface calls it "Programme".
- FR-44: Program groups at a glance. The at-a-glance panels of both segments show each program as one collapsible group with its items in view nested under it; collapsed, the program is visible alone; items without a program remain plain entries. Selection and highlighting work within the groups.
- FR-45: Editable colour labels. The names of the four colours are user-editable in a panel; the legend, the panels, the cards, and exported files carry the user's labels; nothing is predefined beyond the colour names themselves, and no colour is ever assigned from the data.
- FR-46: Configurable at-a-glance columns. A picker chooses which columns the at-a-glance entries show; the defaults are the area, start, and end columns; the choice persists in the work state; both segments' panels follow it. (Amended in v1.3.0, on the owner's decision: the end-role column is among the default columns of fresh work, and opening a work whose saved choice lacks it adds it once, on migration to schema version 7; afterwards the picker governs both segments equally, and the user may switch the column off.) (Amended in v1.3.1: a choice belongs to the list it was made on. A new list, from an import or an empty list, starts with no choice, that is, with the full current defaults (the area, start, and end columns); a saved choice that names a column the work does not have was not made on that work and opens as no choice, with the full defaults; a deliberate choice is respected, with the end column added once on migration as in v1.3.0.)
- FR-47: Annotation layer. Annotations are first-class objects like markers: shapes (rectangle, circle, and freehand polygon that closes when the pointer is pressed near its starting point) and lines (solid, dotted, dashed), in the four item colours, with a selectable fill opacity, an outline black or white, and an optional label. They are drawn and edited (selected, moved, vertices edited, deleted) in the Map segment only; the Presentation segment shows them view-only. (Amended in v1.3.0: the straight-line constraint. While a line or a polygon is drawn, holding Shift or Ctrl snaps the direction of the segment being drawn to the nearest of horizontal, vertical, and the two 45-degree diagonals, live during the stroke; dragging a shape or a vertex with the key held moves it along the nearest of those axes. Annotation labels are rendered in screen space at a constant, readable size at every zoom level, anchored below their shape (on a line, at its middle), while the shapes scale with the map.) (Amended in v1.3.1: one rule for the Map stage, the Presentation stage, and the exported viewer: shapes are geographic and scale with the map; labels are language and keep their size on screen at every zoom, pinned by a browser test on both stages and in the viewer. Superseded in v1.4.0.) (Amended in v1.4.0 on the owner's retest, superseding the v1.3.1 ruling on labels: markers are pins through the map and keep a constant size on screen; annotation labels are lettering drawn on the map and scale with the zoom together with their shapes, as on a paper plan. A label's printed size is a fixed fraction of the background, its longer side divided by 64, so that it is independent of the background's resolution (measured with the demo at 1500 × 950: about 13 pixels of type at the fitted view of the Presentation stage and the viewer, and about 10 pixels on the narrower Map stage, larger when zoomed in); the same annotation carries the same printed size relative to the sheet on the Map stage, the Presentation stage, and in the exported viewer. A browser test pins the proportional behaviour against that fraction on all three surfaces.)
- FR-48: Annotation linkage. A shape or line can be linked to an item as its footprint: it follows the item's visibility everywhere (an item switched off takes its footprint with it, exports included), highlights when the item is selected, and is named in the details panel and the presentation card. Free annotations have their own visibility toggles. Annotations switched off are absent from exports, not hidden.
- FR-49: Honest area measurement. On backgrounds rendered from OpenStreetMap data, whose scale is known, a polygon's real area is shown in true units; on plain images (and on rendered backgrounds whose scale was not recorded) no unit is shown, because none is honest.
- FR-50: PDF export. An explicit action in the Presentation segment produces a PDF document of the visible presentation stage (FR-12): the map with its background, the markers with their numbers and symbols, the annotations with their styles and labels, and the legend, faithful to what is shown, followed by the table of the shown items. The PDF is written entirely client-side as a minimal vector document (paths, circles, text) that uses the base-14 fonts (Helvetica) with WinAnsi encoding, so that the interface languages' characters render correctly, with the background image embedded; no font files, no libraries, no network. A character that WinAnsi cannot represent is replaced by a question mark, and the export dialog states how many characters are replaced before the file is produced (on the owner's decision). What is switched off or removed is absent. The document works offline and lands in the browser's downloads (or the save dialog, where the browser offers one).
- FR-51: PowerPoint export. An explicit action in the Presentation segment produces a minimal, valid .pptx document whose first slide carries the rendered presentation stage as an image, followed by the table of the shown items on native table slides (FR-12). The file is written entirely client-side as a zip with the required OOXML parts and content types; no libraries, no network. What is switched off or removed is absent.
- FR-52: Honest document dialogs. The PDF and PowerPoint exports state their content plainly in their dialogs before the file is produced, in the same pattern as the interactive export (FR-39): what is included, what is excluded, and the approximate file size.
- FR-53: Export content selection. The interactive export's dialog selects what is shared: whole areas (every item with that area value) and individual items, with their markers, cards, and linked annotations; free annotations follow their own toggles. The selection starts from the current visibility state (FR-27). Everything not selected is absent from the exported file, not hidden in it: its data is not embedded. The dialog also chooses which columns the exported cards carry; every column starts chosen, as before, and a column not chosen is absent from the exported data.
- FR-54: Editable symbol labels. The names of the marker symbols are user-editable in a panel, managed like the colour labels (FR-45): one label per symbol, carried by the legend, the symbol pickers, the panels, the cards, and the exported files. A symbol without a label shows its name in the interface language, unchanged (on the owner's decision); labels are data, never meanings built into the application.
- FR-55: Role explanation. Beside the role assignment in the Information segment, a "What do these do?" control explains in plain language what each role feeds: the name the card header and the panels; the start and end the card and the at-a-glance columns; the note the card's headliner; the area the grouping; the status the symbols; the program the grouped numbering; the identifier the comparison.
- FR-56: Reset demo. While the demo is loaded, a "Reset demo" action beside the header's demo label discards the session, after the unsaved-changes confirmation, and loads the pristine demo in one step.
- FR-57: Marker size band. Markers keep a readable, constant size on screen at every zoom level, while annotations (footprints) scale with the map; pinned by a test. (Amended in v1.3.1: the same holds on the Presentation stage and in the exported viewer.) (Amended in v1.4.0: markers keep their constant size on every surface; annotation labels now scale with the map, as FR-47 states.)
- FR-58: Narrow viewer layout. On a narrow viewport (a maximum-width query and a landscape clause for low phone screens, the threshold recorded in the changelog), the exported viewer, and only the viewer, uses a narrow layout, made entirely of one appended media block in the stylesheet and script gated on the same query: the stage fills the viewport height; the "In view" panel and the legend become overlay panels, hidden by default, one open at a time, opened from a compact toggle bar and closed with Escape, a tap outside, or their toggle, with the card's pattern of state, inertness, expanded state, focus return, and reduced motion; choosing an entry in "In view" closes the overlay and opens the card; the header wraps compactly with no horizontal overflow; the card docks at the bottom of the stage with a maximum height and its own scrolling, and shows the values that a narrow entry would shorten in full; the stage does not pass its overscroll to the page; a resize or a change of orientation refits the view, in the narrow layout only. Above the threshold, nothing changes: a browser test compares the desktop layout with that of v1.3.1. The viewer renders no item list on any device (FR-38 as amended in v1.3.1); items without a marker stay unreachable in the viewer.

## Non-goals

- GitHub Pages hosts the generic application build; it never hosts user data, work states, or exported presentation files.
- No automatic data matching, merging, or selection logic. (Amended for FR-14: when an exported file is opened for comparison, its items are paired with the current items by equal values of the identifier column for display only; nothing is merged or changed except through an explicit user action.)
- No hardcoded schema: no fixed column names or formats. (Note for FR-30: the starter columns of an empty list are editable interface text, not a schema; see hard constraint 5.)

- Bounding rectangle: the single ambiguous field is replaced by four explicitly labelled fields in decimal degrees (WGS84), in the order south, west, north, east, with a one-line explanation of the ranges and a generic example value (south 10.000, west 20.000, north 10.020, east 20.030). A comma is accepted as the decimal separator. The place-name search remains the primary route, labelled "recommended"; the rectangle is the secondary route.

A plausible search therefore never pulls an entire region.

Known limitations and notices, stated explicitly:

- The fetch was not verified against the live services or on the hosted page: the development environment has no network access to them. Request interception in the test browser does not apply the browser's cross-origin checks, so it cannot show whether a browser accepts the live services' answers in a page opened from a file. This is stated in the README.
- Using the open services is subject to their usage policies (fair use; the geocoder allows at most about one request per second). Requests are only ever made by explicit user action, one at a time. The hosted page sends its origin as the referrer, as the geocoder's policy asks; a page opened from a file sends none.
- Large .osm files: the file is read whole and parsed on the main thread; files above 50 MB are refused with a message asking for a smaller area. Below that, loading takes time in proportion to the size and the page does not respond meanwhile: in the test browser, synthetic files of 10, 25, and 45 MB took about 4, 11, and 20 seconds. The rendered image is at most 4096 pixels on its longest side, so a large area is drawn with less detail; small details may merge at that scale.
- Relations, including multipolygons, are not interpreted: features that exist only as relations (for example many large lakes and some large buildings) are not drawn. Names and labels are not drawn. Data that is not in the fetched feature classes is not requested.
- The rendered map uses one fixed palette in both interface themes, like an image or PDF background; it is not re-coloured for the dark theme.

- Manual columns cannot yet be removed (only hidden), and imported values of imported columns cannot be edited (FR-10 remains deferred).

- Presets are stored in local storage only when the user saves, removes, or opens a file containing presets; where local storage is unavailable, presets remain available for the session and in saved work-state files.
- The work-state file continues to capture only the features implemented so far; later passes will extend the schema further.

### v0.4.0

Work-state persistence pass (Pass 3).

Delivered units:

1. Work-state file (FR-13): an explicit Save work action writes the complete work state to one local JSON file. Where the browser offers a save dialog (the File System Access API, for example in Chromium-based browsers), the user chooses the file there; elsewhere the file is offered as a local download named mapvibes-work-state.json, and the browser's download settings decide whether the user is asked for a location. The file carries the format name mapvibes-work-state and the schema version field schemaVersion, whose value in this version is 1. It contains: the column mapping (every column of the import with its kept flag and role), the kept columns, and the columns hidden in the list; all ingested rows in ingestion order with all values, their retained or removed status, their colour, and their global sequential number (null for removed rows); the map background embedded as image data (the loaded image file or the rendered PDF page), with its size; every marker with its position in image coordinates and its association to a row; and the view state (the current segment, the map viewport, and the list sorting and filter). To keep the removed status, removed rows are now kept in the work state rather than discarded.
2. Work-state load (FR-13): an explicit Open work action reads such a file and restores the complete state, including the background and the markers, without the original spreadsheet or background file. The file is validated completely before anything changes: a file that is not JSON or not a work-state file, a file whose schema version is not 1, and a damaged or inconsistent file (for example a numbering that breaks the global sequence, a marker on a removed row, or a background that is not embedded image data) are rejected with a clear message and nothing is opened. A background that is not embedded image data is always rejected, so opening a file can never make the browser fetch a resource. Opening over unsaved changes requires an explicit confirmation; declining changes nothing. If the stored background cannot be decoded, nothing is opened.
3. Unsaved-changes awareness: an indicator in the header shows when the work has unsaved changes, and closing or reloading the page with unsaved changes asks the browser to confirm. Content changes count as unsaved changes (import, row removal, colour changes, the background, and placing, moving, or removing markers); view changes alone (segment, zoom and pan, list sorting, filtering, and column visibility) are saved with the work but do not count as unsaved changes. Saving or opening a file clears the indicator; a cancelled save does not. Nothing is written automatically at any time: files are written only by Save work.
4. Defect fix: the theme option labels (Follow system, Light, Dark) now follow the language toggle (FR-19); a regression test covers the switch in both directions, the unchanged option values and current choice, and a stored Swedish preference at start.

Verification: type checking; unit tests of the work-state file (a save and load round trip restoring an identical state, including the embedded background data and marker positions, and byte-identical on a second round trip; rejection of unknown schema versions, of non-work-state files, of non-embedded backgrounds, and of inconsistent numbering, markers, and columns); UI tests of the save flow (save dialog, cancelled dialog, failed write, download fallback), of the open flow (complete restoration in a fresh application instance, an identical file when saved again, confirmation accepted and declined, no confirmation without unsaved changes, unknown schema version, non-work-state file, damaged file, undecodable background), of the unsaved-changes indicator and the unload guard (including that no file is written and nothing is stored by editing or unloading), and of the theme label fix; the build regression suite; and headless-Chromium runs of both built artifacts via file:// with the browser context offline, covering the reload guard, Save through the download route, restoration of the saved file in a fresh page with identical markers, view, counts, and segment, and the confirmation when opening over unsaved changes. The only request made was the local file itself.

Known limitations, stated explicitly:

- The work-state file captures only the features implemented so far. Features added in later passes (for example manually added items, field edits, comments, manual columns, and presentation settings) will extend the schema; such extensions will raise the schema version, and files of an older version will need an explicit migration path in a later pass.
- Marker selection and row selection in the list are transient interaction state and are not saved. The original spreadsheet is not embedded: only the kept columns of the imported rows are saved, so columns not kept at import cannot be recovered from the file, and after opening a file the column mapping cannot be changed (re-importing the spreadsheet starts a new import).
- The native save dialog cannot be driven by browser automation; the save-dialog route is verified with a stand-in in the UI tests, and the download route in the headless-browser run. In browsers without a save dialog, the work is marked as saved once the download is handed to the browser.
- The detail text of a damaged-file message names the inconsistent field in English in both interface languages.
- The work-state file contains the user's data in plain text; it is written only where the user saves it and is never transmitted.
- Pre-existing defect observed during verification and not fixed in this pass (outside its scope): the header row of the list table has no cell for the row-selection column, so each column heading is shown one column to the left of its values.

### v0.2.1

Recovery defect-fix pass over the v0.2.0 delivery. Both built artifacts (the folder build `index.html` and the single-file build `mapvibes-singlefile.html`) rendered a large dump of source text above the application interface. Root causes confirmed and fixed in the shared post-build inlining step:

- The inliner used a replacement string in `String.replace`; JavaScript interprets `$&`, `$'`, and similar sequences in replacement strings, so the xlsx bundle spliced the remainder of the HTML document into the middle of the inlined script. The substitution now uses a replacer function, which is literal.
- The inlined bundle contained `<!--` sequences (inside xlsx regex literals) and one `<script` sequence (inside an xlsx string literal); in HTML script tokenization `<!--` switches the tokenizer to escaped state, `<script` can then enter double-escaped state, and the closing `</script>` is consumed as a state transition instead of closing the element, rendering the remainder of the bundle as page text. A content-agnostic post-build sanitiser is now applied to the entire bundle on every build: `</script` is escaped as `<\/script`, `<!--` as `<\x21\x2D\x2D`, and `<script` as `<\x73cript` — hex escapes that are valid and semantics-preserving inside JavaScript string and regex literals while breaking the HTML tokenizer sequences.

Verification: a build regression test that parses the built document with a model of the browser's script-data tokeniser states and asserts that no script source renders as body text (fails against the deliberately reverted inliner, passes against the fixed one), plus a real headless-Chromium `file://` render of both builds confirming both open directly at the application interface with no source dump. The README Running section now describes the Release archive (download, extract, open) as the primary runnable route, with the development workflow second. No functional requirements were added or changed in this pass; the FR-4 through FR-18 deferrals stand.
