# MapVibes — Functional Specification

Status: v1.15.0 — the phone editor, phase two: the amendments below are recorded before implementation and are the design of record for the pass; the delivered state and its measured figures are in the changelog below.

MapVibes is a static, client-side web application: a spreadsheet-to-map visualisation tool. It has no backend, no database, and no server-side processing. Everything runs locally in the browser.

## Hard constraints

1. Fully client-side static web application (HTML, CSS, JavaScript).
2. No network calls at runtime: no uploads, no analytics, no telemetry, no CDN fetches during use. All fonts, styles, and scripts are bundled locally. The single exception is the explicit, user-initiated, clearly labelled fetch of open map data (FR-31): it is the application's only network operation; it is never made automatically; no user data is ever included in its requests; its result is embedded into the work state like any other background. All other operations, including the exported presentation file, remain fully offline. (Note, v1.5.0: the address of the hosted application appears as plain text in the no-scripts notice of an exported file (FR-59), for the recipient to read; nothing in the application or the exported file fetches it or links to it.)
3. The application must function fully with no internet connection (airplane-mode test applies to every delivery). The guarantee holds at all times except during the labelled open-map fetch (FR-31); with no connection, that control is disabled with a clear message and every other function works.
4. All state remains on the user's device: files are read in the browser and written only on explicit export or save.
5. No hardcoded column names, headers, or business terminology: the application must work with arbitrary header names in any language. (Note for FR-41: the bundled demo is example data, a generic and fictional fixture from example-data loaded through the normal import path; its neutral headers and invented names are data, never used by the application's logic. Amended in v1.3.1: the fixture is carried in example-data in both interface languages, and the demo loads in the interface language; the translations are data of the fixture, not application text, and no logic reads them.) (Note for FR-30, amended in v1.3.0 on the owner's decision: the starter columns of an empty list are interface text in the current language with neutral words (Name, Start year, End year, Note; Namn, Startår, Slutår, Anteckning), created as ordinary, editable manual columns; their roles are assigned by column key, never by name, and no logic reads their labels.) (Note for FR-63 and FR-64, v1.6.0, following the precedent of the starter columns: year series are proposed from a generic pattern, a four-digit year standing alone in a header, never from a word; a column becomes money only when the user assigns it to the budget, forecast, or outcome role, and nothing is inferred from a header's words. The per-work currency unit defaults to SEK as a documented, changeable default shown to the user, never matched against a column and never inferred from the data.)
6. No automatic selection or filtering logic deciding which rows "fit": data cleaning is deliberately a manual process performed by the user. The application provides generic list conveniences only.

## Functional requirements

- FR-1: Ingest a spreadsheet (xlsx) by file drop or file picker; parse all columns; surface parsing errors clearly. Ingestion is direct: importing a spreadsheet populates the list immediately with all of the file's columns, named by the file's own headers, shown as-is; no configuration dialog interrupts the import, and no header names are hardcoded. Columns are shown and hidden in the list itself. Role assignment also takes place in the list: a per-column control in the list header assigns the optional roles identifier, name/title, start date, end date, area/grouping, and status (each role to at most one column). All column data is treated as generic text. The name/title is the display name of an item, used by the list, the marker labels, and the at-a-glance panel; where it is unassigned or empty, the display name falls back to the identifier value, and otherwise to the item's number. (Amended for FR-43 and FR-35: the roles include program and note.) (Amended in v1.7.0: a date cell of the spreadsheet is read as its date, written as the year, month, and day (with the time where it has one), in the calendar it shows; before, real date cells arrived as their raw serial numbers in every surface.)
- FR-2: Support the user's manual cleaning process: present all ingested rows in the list; the user removes rows by hand. The list shall support: sorting by column; setting the marker colour per row; showing and hiding columns; filtering on column values, including empty and non-empty cells in a chosen column; and selecting multiple or all rows for bulk deletion. Show running counts of retained and removed rows.
- FR-3: Assign sequential presentation numbers, starting at 1, globally across all items. When rows are removed or added after numbering, numbers regenerate so the sequence remains continuous. (Amended for FR-17: the global numbering is the default; a grouped numbering by area can be chosen explicitly instead, and switching back restores the global numbering.)
- FR-4: Display a zoomable, pannable background map image supplied by the user.
- FR-5: Allow the user to place, move, and remove numbered markers, with the colours green (default), blue, yellow, and red. (Amended for FR-45, on the owner's decision: green stays the initial colour of a new row; the application never colours items from their data and gives the colours no meanings; the user names them.)
- FR-6: Display a legend at the bottom of the map view. (Amended in v1.9.0: in the Presentation segment and in every exported presentation the legend is used-only, per FR-75; the Map segment's legend keeps the working palette of the work's vocabularies.)
- FR-7: Display a details panel for a selected item. Selecting an item (a line in the list, its marker in the Map segment, or its entry in the at-a-glance panel) opens a details panel showing all of the item's data: number, name/title, colour, symbol, every column with its value, and its comments. The panel follows the selection and closes cleanly. (Amended in v1.6.0: the details panel groups each assigned year series (FR-63) into one line, its year values editable inside the group, with an Economics action that opens the economics view (FR-64) for an item that has economics.)
- FR-8: The main view shows all areas; the user may zoom in or select a box/region of interest to focus on one area.
- FR-9: Allow the user to add items manually (not originating from the spreadsheet), with the same fields, colour coding, sequential numbering, and marker placement as imported items.
- FR-10: Allow the user to edit any item's values, including values that came from an import, in the list and in the details panel; edits count as unsaved changes and are stored in the work state.
- FR-11: Export a single self-contained interactive HTML file (all data, map image, and application logic embedded in one file) that opens locally in any browser with zoom, legend, and per-marker details, requiring no server and no internet connection. This is the primary presentation format. An explicit export action produces one standalone HTML file, the viewer and the work state to be shared embedded in it, that opens by double-click on any machine, fully offline, with no network calls and no dependencies. (Amended in v1.3.0: the interactive export is the primary and most prominent sharing action in the Presentation segment; the PDF and PowerPoint actions sit beside it as secondary actions.) (Amended in v1.10.0: the exported file carries the items' activities inside its work-state island (FR-77), so the viewer renders them in the timeline (FR-78); the export format version is unchanged.) (Amended in v1.11.0: the exported file also carries the events (FR-80) and the costs view's saved window (FR-79) inside its work-state island; the export format version is unchanged.) - FR-22: Segment structure. The application is organised into three segments with a clear flow: Information (list, cleaning, numbering), Map (background, markers, placement), and Presentation (final view and export). Work performed in one segment is never lost by moving to another segment.

- FR-32: Area vocabulary. The area/grouping role is choose-from: each cell of the area column offers a combobox in which an existing value is picked or a new value is typed. The list of values is managed by the user in a panel (add, rename, remove), with an action that collects all values currently present in the column. The list is empty by default and persists in the work state and in presets.
- FR-33: Status role and vocabulary. A column can be assigned the status role; its values are chosen, through a combobox in each cell, from a status list managed by the user in a panel (add, rename, remove, reorder, and assign a symbol from the symbol library to each status). The list is empty by default and persists in the work state and in presets. No status words are predefined.

While it is off, choosing a status never changes any marker's symbol; symbols change only per marker in the Map segment. While it is on, each item whose marker has no manually chosen symbol shows the symbol of its status; a manually chosen symbol is never overridden.

When an area is larger than the area cap, it is reduced about its centre and the reduction is stated with the new edges, for a chosen place as well as for an entered rectangle (which is reduced rather than refused).
- Conservative query: the area fetched at once is at most 0.0025 square degrees (about 5.5 by 5.5 kilometres at the equator); the Overpass query asks the service to stop at 16 MiB of data (maxsize) and after 25 seconds; an answer larger than 16 MiB is not processed; the browser stops waiting after 40 seconds for map data and 15 seconds for a place search; a place search asks for at most 5 results. A plausible search therefore never pulls an entire region.
- Verification: each failure class, the busy state, and cancellation are tested against simulated service responses (unit and UI tests), as before. Verification against the live services remains with the tester: the development environment has no access to them.

Known limitations and notices, stated explicitly:

- The fetch was not verified against the live services or on the hosted page: the development environment has no network access to them. Request interception in the test browser does not apply the browser's cross-origin checks, so it cannot show whether a browser accepts the live services' answers in a page opened from a file. The services send headers that allow requests from any origin, so the fetch is expected to work from file:// as well as from the hosted page; if a browser blocks it from a file-based page, the hosted page or a local .osm file is the alternative, and local .osm loading is always the fully offline route. This is stated in the README.
- Using the open services is subject to their usage policies (fair use; the geocoder allows at most about one request per second). Requests are only ever made by explicit user action, one at a time. The hosted page sends its origin as the referrer, as the geocoder's policy asks; a page opened from a file sends none.
- Large .osm files: the file is read whole and parsed on the main thread; files above 50 MB are refused with a message asking for a smaller area. Below that, loading takes time in proportion to the size and the page does not respond meanwhile: in the test browser, synthetic files of 10, 25, and 45 MB took about 4, 11, and 20 seconds. The rendered image is at most 4096 pixels on its longest side, so a large area is drawn with less detail; small details may merge at that scale.
- Relations, including multipolygons, are not interpreted: features that exist only as relations (for example many large lakes and some large buildings) are not drawn. Names and labels are not drawn. Data that is not in the fetched feature classes is not requested.
- The rendered map uses one fixed palette in both interface themes, like an image or PDF background; it is not re-coloured for the dark theme.
- The fetched data is OpenStreetMap data (licensed under the Open Database Licence); the attribution is drawn into the rendered image. Local .osm files carry no attribution, as their origin is not known to the application.
- Manual columns cannot yet be removed (only hidden), and imported values of imported columns cannot be edited (FR-10 remains deferred).
- The test fixtures for this pass are synthetic: the .osm files describe a fictional town at invented coordinates, as real map extracts would be real-world data.

### v0.4.0

Work-state persistence pass (Pass 3).

1. Work-state file (FR-13): an explicit Save work action writes the complete work state to one local JSON file. ### v0.2.1

Recovery defect-fix pass over the v0.2.0 delivery. Both built artifacts (the folder build `index.html` and the single-file build `mapvibes-singlefile.html`) rendered a large dump of source text above the application interface. Root causes confirmed and fixed in the shared post-build inlining step:

- The inliner used a replacement string in `String.replace`; JavaScript interprets `$&`, `$'`, and similar sequences in replacement strings, so the xlsx bundle spliced the remainder of the HTML document into the middle of the inlined script. The substitution now uses a replacer function, which is literal.
- The inlined bundle contained `<!--` sequences (inside xlsx regex literals) and one `<script` sequence (inside an xlsx string literal); in HTML script tokenization `<!--` switches the tokenizer to escaped state, `<script` can then enter double-escaped state, and the closing `</script>` is consumed as a state transition instead of closing the element, rendering the remainder of the bundle as page text. A content-agnostic post-build sanitiser is now applied to the entire bundle on every build: `</script` is escaped as `<\/script`, `<!--` as `<\x21\x2D\x2D`, and `<script` as `<\x73cript` — hex escapes that are valid and semantics-preserving inside JavaScript string and regex literals while breaking the HTML tokenizer sequences.

Verification: a build regression test that parses the built document with a model of the browser's script-data tokeniser states and asserts that no script source renders as body text (fails against the deliberately reverted inliner, passes against the fixed one), plus a real headless-Chromium `file://` render of both builds confirming both open directly at the application interface with no source dump. The README Running section now describes the Release archive (download, extract, open) as the primary runnable route, with the development workflow second. No functional requirements were added or changed in this pass; the FR-4 through FR-18 deferrals stand.
