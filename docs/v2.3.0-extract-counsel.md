# Extract counsel — v2.3.0 demo redesign (Unit 1)

Base: main at ac84390 (v2.2.2 as released), clean tree, branch wip/demo-redesign-v2.3.0. This counsel is produced before anything is cut, as the v2.3.0 directive requires: it names the extract areas' bounds, the expected archive weight of each, and every limit the application's offline import path places on extract size, with the recommendation. All network measurements below were made from the build sandbox with node fetch (the sandbox blocks curl); the results are recorded, not assumed.

## 1. The application's own import path and its limits

The application's own path for open map data is the .osm import (FR-31): a file is read whole and parsed by parseOsm (src/osm.ts), projected and planned by planRender, drawn onto a canvas by renderPlanToDataUrl (src/osmrender.ts), and set as the background by useOsmText (src/mapstage.ts:393). Fetched data differs only in that its requested bounds and the attribution string are supplied alongside (fetchpanel.ts:210). The limits on the offline import path:

- Hard size cap: MAX_OSM_BYTES = 50 MiB (src/osm.ts:45). A larger .osm file is refused before it is read, with the osmTooLarge message ("larger than 50 MB. Choose a smaller area."). The same 50 MB cap applies to spreadsheets and presentation files.
- The file is read whole and parsed on the main thread (no streaming), so the practical ceiling is well below the cap; the parse is DOMParser over the whole text.
- Render bound: the longest side of the rendering is capped at MAX_RENDER_SIDE = 4096 px, preferred PREFERRED_RENDER_SIDE = 3000 px (src/osm.ts). Pixel area is therefore bounded (at most 4096 squared) whatever the extract's extent; the Web Mercator projection is stored with the background, so the scale is known (FR-49).
- The application's own FR-31 fetch (runtime, in the user's browser; src/openmap.ts) caps a request at MAX_FETCH_AREA = 0.0025 square degrees (a larger area is reduced about its centre and the reduction is stated), at MAX_FETCH_BYTES = 16 MiB of answer (the Overpass query asks maxsize 16 MiB and an answer above it is not processed), with 25 s service and 40 s browser timeouts. Both proposed extract areas below are inside the area cap, so the same areas are also fetchable in-app.
- Bundling constraint: the demo's background is inlined into the single-file build as text (src/demo.ts imports the fixture with ?raw), so the bundled extract's weight lands in dist/index.html (2.78 MB at v2.2.2). This is a practical reason to keep the bundled extract lean, not a hard cap.
- Attribution as data: the framework carries the attribution as the fetchAttribution string in both interface languages ('© OpenStreetMap contributors', a listed translation-parity exception in tests/ui/translation-parity.test.ts), and renderPlanToDataUrl draws it into the rendered image itself (src/osmrender.ts:72-81), so an exported presentation carries it inside the background image. The demo load currently passes no attribution; the v2.3.0 redo passes it, so the demo's background carries the attribution exactly as a fetched one does, in both languages.

## 2. Reachability of the route from the build environment (measured)

| Service | Result from the sandbox |
| --- | --- |
| nominatim.openstreetmap.org (geocoding) | Reachable; HTTP 200, place search and bounding boxes returned |
| api.openstreetmap.org (/api/capabilities, /api/0.6/map) | Reachable; /api/0.6/map returns full OSM XML for a bounding box; its own caps: at most 0.25 square degrees and at most 50,000 nodes per call |
| download.geofabrik.de | Reachable; the Sweden extract is on the order of 1.4 GB (pbf), not viable for a sandbox cut — recorded, not used |
| overpass-api.de and mirrors lz4/z.overpass-api.de | Connection refused from the sandbox |
| overpass.kumi.systems, overpass.private.coffee | Hang (no answer within 60 s) |
| overpass.nchc.org.tw, overpass.openstreetmap.ru | Connection refused |
| overpass.openstreetmap.fr | HTTP 403 |
| overpass.osm.ch | Reachable, but serves Switzerland only; empty answers for Sweden |

Verdict: the route is not blocked. The application's runtime FR-31 fetch uses Overpass, which a real browser reaches; from this build sandbox the reachable official route is Nominatim for place bounds plus the OSM API /api/0.6/map for the data, tiled so that every call stays under its 50,000-node cap. The cut is therefore the merge of tiled /api/0.6/map answers, deduplicated, kept to the application's own selector set — the eight tag keys of overpassQuery in src/openmap.ts (highway, building, natural, water, waterway, railway, leisure, landuse) plus their nodes — with edit metadata stripped (parseOsm reads only id/lat/lon on nodes and id/nd/tag on ways). That form is exactly what the application's own Overpass fetch returns for the same area, so the bundled demo background equals an in-app fetch of the area, and it enters the application only through the application's own import path (parseOsm to planRender to renderPlanToDataUrl via useOsmText) — never hand-embedded, never a screenshot.

## 3. The two extract areas

### Area A — Slottskogen and Änggårdsbergen, Gothenburg (this pass, v2.3.0)

- Recommended bounds: south 57.6690, west 11.9310, north 57.7050, east 11.9530 — 0.0360° × 0.0220° = 0.000792 square degrees, about 4.0 km north-south by 1.3 km east-west at 57.69° N. Both parks lie inside: the geocoded Änggårdsbergen relation (forest) bounds are 57.6529350-57.6845761 / 11.9389199-11.9887511, and Slottskogen's geocoded features (information boards at 57.6840174 / 11.9440208 and 57.6881198 / 11.9401855) lie inside the park within the bounds.
- Measured weight of the enclosing probed box (south 57.6680, west 11.9290, north 57.7060, east 11.9540; 0.000950 sq deg): 12 of 12 tiles answered HTTP 200; 39.0 MiB raw XML, 145,617 nodes, 17,704 ways; selector-matched about 10,910 ways and 69,604 nodes. The recommended tighter bounds scale to roughly 30 MiB raw. The lean selector-filtered, metadata-stripped archive is expected at roughly 8 to 15 MB; the exact weight is recorded at the cut.
- Aspect note: the area is tall (about 1 : 3); the renderer fits the longest side to 3000 px, so the background renders at roughly 1000 × 3000 px. Demo marker positions are fractions of the background, so they carry to any render size.

### Area B — Planteringen and Helsingborg south (pass 35)

- Recommended bounds: south 56.0220, west 12.6780, north 56.0460, east 12.7140 — 0.0240° × 0.0360° = 0.000864 square degrees, about 2.7 km north-south by 2.0 km east-west at 56.03° N. Planteringen (geocoded as the Stadsparken way/park, Helsingborg: bounds 56.0417263-56.0436680 / 12.6968271-12.7006605) lies inside; the bounds extend south over the Söder districts to 56.022.
- Measured weight: 6 of 6 tiles answered HTTP 200; 9.3 MiB raw XML, 26,227 nodes, 3,588 ways; selector-matched about 3,237 ways and 19,491 nodes. The lean archive is expected at roughly 4 to 6 MB.

## 5. Recommendation

1. Cut area A now, in tiled /api/0.6/map calls over the recommended bounds (tiles of about 0.01° × 0.008°, each under the 50,000-node cap, at least one second apart), merge and deduplicate into one well-formed .osm with a bounds element, keep the application's own eight selectors and their nodes, strip edit metadata. Record the exact bounds and byte weight in the changelog.
2. Bring the extract into the application only through its own import path (useOsmText), as vector data, with the attribution carried as data (fetchAttribution, both interface languages) drawn into the rendered background as for fetched data; disclose the attribution in both languages.
3. Hold area B's identical procedure for pass 35 with the bounds above; the counsel's measurements are its starting point, and the cut there records its own exact weight.
4. Keep example-map.osm (the synthetic fictional town) in example-data as the generic .osm test fixture it is documented to be; the product bundles exactly one demo, and after v2.3.0 that demo's background is the parkland extract.

## 6. Reconciliation of the example-data rule, disclosed

ENVIRONMENT_DISCIPLINE rule 7 bars real-world data in the repository's example fixtures. SPECIFICATION.md, the authority of record, keeps the two categories apart: hard constraint 5's FR-41 note requires the demo's list fixture (headers, invented names, vocabularies, comments) to be generic and fictional, and the v2.3.0 directive preserves exactly that — the invented names, columns, and data are unchanged; FR-31 separately defines open map data as legitimate background data carried with its attribution. The redo replaces only the background with ODbL-licensed OpenStreetMap data whose attribution is carried as data in both interface languages. The two stand together; example-data/README.md will carry an explicit note for this one map fixture. This reconciliation is reported here and in the pass report rather than silently resolved.
